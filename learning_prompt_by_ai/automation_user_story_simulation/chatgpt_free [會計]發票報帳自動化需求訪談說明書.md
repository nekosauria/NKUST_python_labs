## # 自動化五問

1. 起點: 申請人上傳發票照片（報帳/請款流程觸發）

2. 終點: 會計完成發票審核並決定是否放款（核准或退回）

3. 判斷:
   - Trigger condition（觸發條件）:
     - 發票照片上傳完成（upload event）
   - business rule（關鍵規則 / keyword / threshold）:
     - 發票金額需與申請金額一致或在允許差異範圍內
     - 發票格式合法（可辨識公司抬頭 / 統編 / 日期）
     - 是否重複報帳（invoice duplication check）
     - 發票是否有效（未過期 / 合法稅務格式）

4. 失敗處理:
   - API / 系統失敗:
     - OCR / 發票辨識服務失敗需 log
     - 檔案上傳失敗需提示重新上傳
   - retry 機制:
     - OCR 辨識失敗可重試解析（最多 N 次）
     - 審核流程可重新提交或補件
   - fallback（人工處理）:
     - 進入人工審核 queue（會計手動處理）
     - 無法辨識發票需人工補判或退回申請人

5. 值得做嗎:
   - ROI summary（時間 / 人力 / 風險）:
     - 時間：降低會計逐張比對與查核時間
     - 人力：可部分自動化報帳初審流程
     - 風險：降低錯付、重複報帳與假發票風險
     - 自動化：中（OCR + rule check 可提升效率，但仍需人工覆核）
     - 可追蹤性：完整保留申請、發票與審核紀錄

---

## # 需求點（Functional Requirements）

- 系統需支援申請人上傳發票照片（image upload）
- 系統需具備 OCR 發票辨識能力（或第三方服務整合）
- 系統需自動解析發票內容（公司、金額、日期、統編）
- 系統需比對申請金額與發票金額一致性
- 系統需檢查發票是否重複使用（duplicate detection）
- 系統需提供會計審核介面（approve / reject）
- 系統需記錄所有審核與發票資料（audit log）
- 系統需支援異常案件人工處理流程（manual review queue）

---

## # 缺少資訊（Missing Requirements）

### 1. 業務規則缺失
- 金額允許誤差範圍（是否允許 ±5%）
- 哪些費用類型需要發票（全額 / 部分）
- 是否分不同審核層級（小額自動 / 大額人工）

### 2. 系統整合缺失
- OCR 服務選型（Google Vision / AWS Textract / 自建）
- ERP / 財務系統是否需對接
- 發票資料庫（是否已有國稅局或電子發票 API）

### 3. 流程 / 權限缺失
- 誰有權限審核（會計 / 主管 / 財務）
- 是否需要雙重審核（dual approval）
- 拒絕後是否允許重新申請

### 4. 資料格式缺失
- 發票資料 schema（invoice_no / amount / date / vendor）
- 圖片格式與大小限制
- 審核紀錄格式與保存期限

## # 判斷價值（Business Value）

1. 時間節省
- 減少會計人工逐張比對發票時間

2. 風險降低
- 降低錯付、重複報帳與假發票風險

3. 自動化程度提升
- 從純人工審核轉為 OCR + rule-based 半自動流程

4. 可追蹤性
- 發票、申請、審核全流程可完整追蹤與稽核
